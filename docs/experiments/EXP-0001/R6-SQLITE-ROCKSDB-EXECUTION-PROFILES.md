# R6 SQLite and RocksDB Execution-Profile Freeze

**Status:** complete documentation design; not built, implemented, configured, executed, or empirically validated
**Freeze date:** 2026-08-27
**Profiles:** `EXP1-B2-SQLITE-3.53.4-WAL-1` and `EXP1-B3-ROCKSDB-11.8.1-WAL-1`

## 1. Decision and evidence boundary

R6 resolves BLK-018 and the B2/B3 design portion of BLK-019. It freezes source identities, build recipes, native API boundaries, database mappings, requested settings, later effective-setting evidence, and D0–D3 classifications. It does **not** resolve BLK-015, BLK-026, implementation, executable validation, platform survival, or empirical equivalence. A future series manifest must supply the compiler/toolchain and final R4 path before either frozen recipe can be executed.

The profiles preserve [ADR-0002](../../adr/ADR-0002-foundational-canonical-history-constraints.md): canonical history alone is authoritative; a row, key/value, database WAL, WAL index, memtable, SST, checkpoint, cache, or database-native sequence is derived or lifecycle evidence. A successful database call and surviving bytes do not promote D0/D1 observations. D2 canonicality is conditional on the R3 lifecycle, the exact R4 platform contract, verified effective configuration, and later recovery evidence. EXP-0001 commits one event at a time; a SQL transaction or `WriteBatch` is never an atomic multi-event project capability.

### 3.2 One-event physical mapping

Both adapters receive the same already-validated R3 candidate. They store the complete eventual versioned semantic-envelope bytes unchanged plus explicit lookup fields; neither engine constructs project identity, sequence, or time.

| Semantic item | SQLite row | RocksDB key/value |
|---|---|---|
| Event identity | `event_id BLOB NOT NULL UNIQUE CHECK(length(event_id)=16)` | key: byte `0x45` followed by the 16 event-id octets |
| Request/retry identity | `request_id BLOB NOT NULL UNIQUE CHECK(length(request_id)=16)` | key: byte `0x52` + request-id octets maps to the event-id; conflict or differing normalized request fails closed |
| Replay sequence | `sequence INTEGER NOT NULL UNIQUE CHECK(sequence>0)` | key: byte `0x53` + unsigned 64-bit big-endian sequence; value maps to event-id |
| Fact bytes | `envelope BLOB NOT NULL`; provisional then final byte equality is mandatory | event-key value is the exact versioned physical value defined below, containing the unchanged provisional or final envelope |
| Time fields | remain encoded distinctly in the envelope; nullable `durability_time_ns INTEGER` duplicates the value only after finalization | remain encoded distinctly in the envelope; the event-key physical-value header duplicates durability time only after finalization |
| References/payload | exact envelope bytes; no SQL interpretation | exact envelope bytes; no RocksDB merge/transform |
| Native order | rowid/B-tree/WAL order is diagnostic | internal sequence/WAL/memtable order is diagnostic |

SQLite schema: one table `events(sequence INTEGER NOT NULL UNIQUE CHECK(sequence>0), event_id BLOB NOT NULL UNIQUE CHECK(length(event_id)=16), request_id BLOB NOT NULL UNIQUE CHECK(length(request_id)=16), durability_time_ns INTEGER, envelope BLOB NOT NULL, PRIMARY KEY(sequence)) WITHOUT ROWID;` and no other user table, trigger, generated column, index, foreign key, view, or virtual table. D1 leaves durability time null. One prepared `INSERT` is executed inside one explicit transaction per event; D2 uses the separately prepared final `UPDATE`.

RocksDB has exactly three keys per event and no metadata or fourth key: `E || event_id`, `R || request_id`, and `S || sequence_be_u64`, with the one-byte domains `E=0x45`, `R=0x52`, and `S=0x53`. The `R` and `S` values are exactly the 16 event-id octets and never change. The `E` value is `0x01 || 0x00 || provisional_envelope` before finalization and `0x01 || 0x01 || durability_time_be_i64 || final_envelope` afterward; `0x01` is the physical-value format version, the second octet is the provisional/final state, and the signed durability time is an eight-octet two's-complement big-endian value duplicated from the unchanged final envelope. The first write is one fresh `WriteBatch` with exactly three ordered `Put`s—`E`, then `R`, then `S`—and therefore consumes exactly three consecutive native sequence numbers. The D2 final write is a fresh batch with exactly one `Put` overwriting only `E` and consumes exactly one further native sequence number; `R` and `S` are no-ops and must not appear in that batch. D1 performs only the first batch. RocksDB uses exactly one default column family, `Put` operations only, and one `DB::Write` call per batch. Each batch represents the same one semantic event; multi-event batches remain prohibited. Merge, delete, range-delete, transactions, snapshots, secondary instances, and user timestamps are prohibited.

Duplicate retry reads all three RocksDB keys (or the complete SQLite row and uniqueness mappings) before acting. Exact normalized-request/event/sequence/physical-value equality returns the existing provisional or final outcome according to R3. All three RocksDB keys absent permits the first batch; an exact provisional three-key mapping permits only reconciliation or the one-`Put` final batch; an exact final mapping is a no-op returning the existing outcome. Any partial mapping, unexpected fourth key, wrong value-state/time/envelope bytes, divergent identity, duplicate sequence, cross-identity mapping, or native sequence range other than the frozen three-then-one ranges is terminal ambiguity. Native uniqueness or batch atomicity supports detection but never replaces canonical lifecycle evidence.

## 4. B2 SQLite WAL profile

### 4.1 Open, configure, schema, and transaction sequence

1. The setup connection alone uses `sqlite3_open_v2` with `SQLITE_OPEN_READWRITE | SQLITE_OPEN_CREATE | SQLITE_OPEN_NOMUTEX`, URI processing disabled, and VFS argument null only after recording `sqlite3_vfs_find(NULL)->zName`. Require a newly created empty database in rollback-journal mode, enable extended result codes, set `PRAGMA page_size=4096`, and read back exactly `4096` before WAL activation. Any pre-existing database or other page size fails closed.
2. On that setup connection issue `PRAGMA journal_mode=WAL` and require the returned value and a separate readback to be `wal`. Only then set and read back `PRAGMA synchronous=NORMAL` for B2-D1 or `FULL` for B2-D2, `PRAGMA wal_autocheckpoint=0`, `PRAGMA journal_size_limit=-1`, `PRAGMA locking_mode=NORMAL`, `PRAGMA temp_store=MEMORY`, `PRAGMA cache_size=-2000`, `PRAGMA mmap_size=0`, `PRAGMA busy_timeout=0`, `PRAGMA foreign_keys=OFF`, `PRAGMA recursive_triggers=OFF`, and `PRAGMA trusted_schema=OFF`.
3. Create the exact schema in section 3.2 in its own setup transaction, close cleanly, and preserve the close result. Schema/setup/checkpoint time is outside ingestion.
4. The measured writer and recovery writer each use `SQLITE_OPEN_READWRITE | SQLITE_OPEN_NOMUTEX` with no `SQLITE_OPEN_CREATE`; the independent observer uses `SQLITE_OPEN_READONLY | SQLITE_OPEN_NOMUTEX`. All use URI processing disabled and the recorded null/default VFS. A missing or substituted database must return an open failure and must never be created. Each connection enables extended result codes, verifies `page_size=4096` and `journal_mode=wal`, applies the applicable connection-local settings from step 2, and reads back every setting before use. Connections are never shared concurrently.
5. For each event execute `BEGIN IMMEDIATE`, the one prepared `INSERT`, then `COMMIT`. Acknowledgement and visibility follow section 4.3. No savepoint, implicit transaction, multi-event transaction, attached database, shared cache, read-uncommitted mode, or concurrent writer is allowed.
6. Automatic and application checkpoints are prohibited during measured ingestion. After the measured interval, record `sqlite3_wal_checkpoint_v2(..., SQLITE_CHECKPOINT_PASSIVE, ...)`; it is observation/cleanup, not part of any event's commit. A busy/incomplete or unsolicited checkpoint invalidates the run.

### 4.2 Effective-setting and physical evidence

Before and after every run retain the numeric/string results of all PRAGMAs above plus `PRAGMA database_list`, `PRAGMA compile_options`, `sqlite3_libversion()`, `sqlite3_sourceid()`, `sqlite3_threadsafe()`, VFS name, autocommit state, schema SQL/hash, prepared statement SQL/hash, database/WAL/SHM presence and sizes, WAL checkpoint counters, initial-state classification (new only for the primary profile), connection count, page/cache status counters, and every extended result code/error offset/message. Verify `SQLITE_THREADSAFE=1`, omit/load-extension prohibition, and absence of unexpected compile options rather than assuming defaults.

The future physical oracle must correlate request/event/sequence to the queried row, exact envelope bytes, WAL frames/commit marks appropriate to the pinned format, acknowledgement record, visibility probe, close/reopen result, checkpoint counters, and recovery result. WAL/SHM bytes or a commit mark alone never prove project canonicality. Any requested/effective mismatch, unexpected writer/checkpoint/schema object, unreadable PRAGMA, or unknown compile option fails before measurement.

### 4.3 D-mode lifecycle and recovery

- **D1:** after successful `COMMIT` with `synchronous=NORMAL`, probe the same connection and a separately opened read-only observer, then record provisional visibility and acknowledge only as D1. No durability time or canonical event is created. Loss after process/OS/power fault remains permitted by the project classification.
- **D2:** `FULL` is required. The adapter submits the provisional event, waits for successful `COMMIT`, immediately samples the R3 OS-realtime durability time, constructs the complete envelope, and performs a second single-event `BEGIN IMMEDIATE`/`UPDATE`/`COMMIT` to persist that immutable final value. Only the second successful commit is the conditional establishment boundary; then visibility probes precede acknowledgement. Failure or uncertainty before it exposes no canonical event and requires exact-candidate reconciliation. This two-boundary mapping preserves the R5/R3 post-synchronization durability-time invariant rather than backdating time into the first commit.
- **Recovery:** `sqlite3_close` must return `SQLITE_OK`; close error stops acknowledgements and reconciliation decides. Reopen with the non-creating recovery flags and same VFS/settings from section 4.1, allow only SQLite's documented WAL recovery, verify integrity/error results and exact rows, then apply the EXP-0000 oracle. `SQLITE_BUSY`, `LOCKED`, `FULL`, `IOERR*`, `CORRUPT`, `NOTADB`, `READONLY*`, `CANTOPEN*`, `PROTOCOL`, `SCHEMA`, constraint, commit, rollback, close, or recovery ambiguity is fail-closed; record extended code and never retry an uncertain commit as a new candidate.

SQLite `FULL` expresses documented synchronization intent, not stable-media, PLP, torn-write, or power-loss proof. D2 remains conditional on BLK-015 and later fault evidence.

## 5. B3 RocksDB WAL profile

### 5.1 Open and complete options freeze

Use three phase-specific opens while preserving one semantic/configuration profile. Initial creation alone calls `DB::Open` with `create_if_missing=true` and `error_if_exists=true` and requires an absent database path inside the designated empty parent directory; after setup it closes through section 5.3. The measured writer then calls `DB::Open` with `create_if_missing=false` and `error_if_exists=false`, as does every recovery reopen. Before every non-creation open, require the expected directory plus `CURRENT`, the expected database identity, and exactly the default column family; absence, substitution, unexpected identity or column family, or accidental creation fails closed. No independent instance is open during measured ingestion: pinned `db.h` declares the concurrent `DB::Open`/`DB::OpenForReadOnly` combination undefined for the read-only instance, and this profile does not claim independent-instance visibility.

Across those phase-specific existence flags, explicitly select `paranoid_checks=true`, `use_fsync=true`, `manual_wal_flush=false`, `atomic_flush=false`, `two_write_queues=false`, `unordered_write=false`, `allow_concurrent_memtable_write=false`, `enable_pipelined_write=false`, `avoid_flush_during_recovery=true`, `avoid_flush_during_shutdown=true`, `max_background_jobs=1`, deprecated `max_background_compactions=-1`, deprecated `max_background_flushes=-1`, `max_open_files=-1`, `wal_dir` equal to the DB directory, `wal_recovery_mode=kAbsoluteConsistency`, `WAL_ttl_seconds=0`, `WAL_size_limit_MB=0`, and `wal_compression=kNoCompression`. The two deprecated fields remain at their pinned sentinel defaults so they cannot rewrite `max_background_jobs`; the resulting ceiling is one shared background job total, therefore at most one flush or compaction job can run at once.

The one default column family explicitly selects: bytewise comparator; no merge operator, compaction filter, prefix extractor, table-properties collector, or user timestamp; `write_buffer_size=64 MiB`, `max_write_buffer_number=2`, `min_write_buffer_number_to_merge=1`, `compression=kNoCompression`, `bottommost_compression=kDisableCompressionOption`, level compaction, `num_levels=7`, `level0_file_num_compaction_trigger=4`, `level0_slowdown_writes_trigger=20`, `level0_stop_writes_trigger=36`, `target_file_size_base=64 MiB`, `max_bytes_for_level_base=256 MiB`, `disable_auto_compactions=true`, block-based table, 4 KiB blocks, `no_block_cache=true`, `block_cache=nullptr`, `cache_index_and_filter_blocks=false`, `pin_l0_filter_and_index_blocks_in_cache=false`, no Bloom filter, `persistent_cache=nullptr`, and no prepopulate cache. Both cache settings and both null pointer states must appear in constructed-option and effective evidence; a null block-cache pointer without `no_block_cache=true` is invalid because pinned v11.8.1 may create its internal cache. All remaining `DBOptions`, `ColumnFamilyOptions`, `BlockBasedTableOptions`, `WriteOptions`, and environment defaults are enumerated from the pinned headers into the later series record even when they do not affect this question.

Every event uses `WriteOptions.disableWAL=false`, `ignore_missing_column_families=false`, `no_slowdown=false`, `low_pri=false`, and `memtable_insert_hint_per_batch=false`; `sync=false` for B3-D1 and `sync=true` for B3-D2. Each call has a fresh one-event batch as section 3.2 defines. No `WriteBatchWithIndex`, transaction DB, rate limiter, statistics callback, listener, custom `Env`, ingest-external-file, manual WAL flush, explicit `FlushWAL`, memtable flush, or compaction occurs during ingestion.

The named measured visibility context is `B3-same-instance-reader-v1`: immediately after the applicable successful `DB::Write`, the measured writer invokes `DB::Get` on that same `DB` instance, default column family, once for each of the exact `E`, `R`, and `S` keys. It uses one explicitly constructed `ReadOptions` with `snapshot=nullptr`, `verify_checksums=true`, `fill_cache=false`, and `read_tier=kReadAllTier`; every other field remains at its pinned v11.8.1 default and is enumerated in the field-complete series manifest. The probe must return OK and byte-equal values for all three keys; NotFound, another status, or any mismatch fails closed. For D1 this context is the named provisional reader; after the D2 conditional establishment boundary it is the named canonical reader. This same-instance context satisfies the EXP-0000 declared-reader contract but supplies no concurrency or independent-instance evidence.

### 5.2 Effective-setting and physical evidence

Before and after a run retain `GetOptions`, `GetDBOptions`, the options-file contents/digest, `GetLiveFilesMetaData`, sorted WAL metadata from `GetSortedWalFiles`, database identity/session identity, `GetLatestSequenceNumber`, column-family list, all relevant `rocksdb.*` properties, background-error/status output, LOG/manifest/options/current file identities, WAL/SST sizes, and literal serialized option values. ### 5.3 D-mode lifecycle and recovery

- **D1:** `sync=false`; successful `DB::Write` and the immediate `B3-same-instance-reader-v1` `DB::Get` probe are recorded, followed by provisional D1 acknowledgement only. The probe is named provisional visibility, not independent-instance visibility. OS flushing or later SST survival cannot upgrade it.
- **D2:** `sync=true` and `use_fsync=true`. The first successful three-`Put` single-event batch establishes the exact provisional mapping; immediately sample durability time, construct the final envelope and event-key value, and issue the exact one-`Put` sync=true final batch from section 3.2. Only successful return from this second write is the conditional establishment boundary. The `B3-same-instance-reader-v1` probe then records named canonical-reader visibility before acknowledgement; it does not test another instance. Error/uncertainty reconciles all three exact keys, values, and native sequence ranges; no new identity or sequence is allocated, and an already exact final mapping is a no-op.
- **Recovery:** for an orderly close, prohibit `Flush`, `FlushWAL`, `SyncWAL`, compaction, and any separately requested background wait; first capture all available background status, call pinned v11.8.1 `DB::Close()`, preserve its complete returned `Status`, and delete/release the DB pointer only after `Close()` returns. A non-OK close status fails closed and stops new acknowledgements. Reopen with the non-creating recovery option set and `kAbsoluteConsistency`; require the expected identity and default column family before applying the exact three-key/final-value oracle. Any optional `OpenForReadOnly` inspection is permitted only after the measured writer has closed, uses `create_if_missing=false`, `error_if_exists=false`, and `error_if_wal_file_exists=false`, and remains a separate non-performance recovery/inspection phase; it cannot retroactively supply measured per-event visibility. Any status error, absent or substituted database, corrupted/truncated WAL refusal, divergent value, partial mapping, extra key, missing acknowledged candidate, or sequence conflict fails closed. `avoid_flush_during_shutdown=true` governs shutdown; any observed flush or background work invalidates the primary run rather than being hidden. Later fault testing must distinguish process crash, OS crash and power loss under R4; recovery success alone proves no stronger medium guarantee.

Every non-OK `Status` from open, write, read, property, close-path/background, or recovery stops new acknowledgements and is preserved with code/subcode/severity/string. `NoSpace`, I/O, corruption, invalid argument, unsupported, shutdown, aborted, busy, timed out, incomplete, expired, try-again, column-family-dropped, and unknown status are never silently retried. Delayed/background errors cannot demote an already accepted fact; they halt new acceptance and make violated recovery promises correctness failures.
